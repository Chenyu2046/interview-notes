
### 清洗数据
将全部网页的标签全部去掉，得到 title content url（\3分隔），网页之间（\n）分隔

### 建立索引
`倒排索引 = 关键词 + 倒排拉链(vector<倒排结构体>)  
`&&  正排索引 = 文档id + 文档信息结构体`
1. 索引结构体：title content url id
2. 正排索引：vector(id, 结构体)
3. 按行读取清洗好的数据，填充结构体，根据当前索引大小设置id值（随着塞入结构体数量的增加而增加），放入正排索引中，返回当前正排结构体。
4. 注意，每定义好一个正排结构体（也就是添加一个索引），就会根据当前的正排结构体，定义一个倒排结构体
5. 建立倒排索引函数接受一个正排结构体，将正排结构体title和content分开，利用jieba进行分词，然后分别进行词频统计（title，content（分词词频）），然后放到词频统计表（string，word_cnt）
6. 根据词频统计表，定义好当前倒排结构体（id, keyword,weight）,
7. 最后根据，keyword + 倒排结构体 -> 倒排索引
```c
	//先看看倒排索引里面有没有，该key，
	//1.有的话指向该键值对，然后直接添加倒排结构体到value
	//2.没有，新开一个键值对，然后再添加到value
	InvertedList &invertedlist = inverted_index[c.first];

	invertedlist.push_back(std::move(iinfo));
```
8. 注意，词频统计表（局部变量）对于每个文档都会更新，而在建立倒排索引的最后会将相关数据全部存到倒排索引里面（全局变量）
9. `一个文档->多个关键词->一个词频统计表->多个倒排结构体->多个倒排索引`
10. 查询流程：输入关键词->在倒排索引查询key->查到->在倒排拉链中进行权重排序->返回最高权重倒排结构体->获取该结构体id->通过id查询正排索引->获取正排结构体->返回信息



# 问题

## **一、正/倒排索引**

**问题 1️⃣：你是如何从零实现正排和倒排索引的？底层数据结构是怎么选的？**

- **正排索引**：使用 `std::vector<FileInfo>`，每个 `FileInfo` 包含 `title`、`content`、`url`、自增 `id`。通过 vector 大小自动分配唯一 id。
    
- **倒排索引**：使用 `std::unordered_map<std::string, std::vector<InvertedInfo>>`，key 为分词关键词，value 为该词出现的文档列表，每条倒排信息记录文档 id 和权重。
    
- **流程**：按行读取清洗后的数据 → 构建正排索引 → 根据正排内容分词 → 统计 title/content 词频 → 构建倒排索引并存入映射表。
    

---

**问题 2️⃣：倒排索引里标题和正文的权重是如何设计的？**

- 权重公式：`weight = X * title_count + Y * content_count`
    
- 选择 X=10, Y=1，让标题权重大于正文，保证排序时多关键词相关性更高。
    

---

**问题 3️⃣：多个关键词匹配同一文档时去重和聚合怎么处理？**

- 使用 `unordered_map<doc_id, InvertedDedup>` 累加权重并记录所有匹配关键词。
    
- 最终生成去重后的列表用于排序和展示，避免重复文档。
    

---

**问题 4️⃣：数据量上亿，倒排索引如何优化？**

### **1️⃣ 节点压缩（InvertedInfo 压缩）**

- 当前实现：每个倒排节点 `InvertedInfo` 存储 `keyword`、`id`、`weight`
    
- 问题：文档量上亿时，每个节点占用的内存累积非常大
    
- 优化策略：
    
    1. **去掉冗余字段**：`keyword` 已经在倒排表的 key 中，不需要每个节点重复存储
        
    2. **ID压缩**：文档 ID 可使用 `uint32_t` 或差分编码（delta encoding），存储连续 ID 的增量
        
    3. **权重压缩**：权重可以用 `int16_t` 或定点数表示，减少每个节点字节数
        
- 效果：内存占用可降低 50% 以上，允许在内存中存更多倒排节点
    

---

### **2️⃣ 跳表（Skip List / 带跳跃的倒排链）**

- 当前实现：倒排拉链是 `vector<InvertedInfo>`
    
- 问题：查询多关键词时，需要扫描整个拉链，成本高
    
- 优化策略：
    
    1. 在倒排链中增加**跳跃指针**，形成跳表结构
        
    2. 查询时先跳跃查找，再顺序扫描，快速定位目标 ID
        
    3. 特别适合高频词的倒排链，可以减少扫描 70%-90% 节点
        
- 效果：**查询效率显著提升**，尤其是多关键词交集和 top-K 排序场景
    

---

### **3️⃣ 内存映射（mmap）**

- 当前实现：索引全部加载到内存
    
- 问题：上亿文档时，单机内存可能装不下整个索引
    
- 优化策略：
    
    1. 将倒排索引存储在磁盘文件中
        
    2. 使用 `mmap` 将文件映射到进程地址空间，按需读取
        
    3. 操作像访问内存一样，不用一次性加载全部索引
        
- 效果：
    
    - 大幅降低内存占用
        
    - 保持查询性能，操作系统会自动管理页缓存

# 解决困难
### **正/倒排索引构建困难**

**困难**：

- 文档数量大（数十万甚至上亿），如何保证内存占用合理。
    
- 多关键词匹配时如何去重并累加权重。
    
$H_2O$ 或 $x_n$
**解决方案**：

- 正排索引使用 `vector<FileInfo>`，倒排索引使用 `unordered_map<string, vector<InvertedInfo>>`，保证 O(1) 查找和顺序存储。
    
- 多关键词匹配时，使用 `unordered_map<doc_id, InvertedDedup>` 对每个文档去重，累加每个关键词权重，同时记录出现的关键词列表。
    

---

### **2️⃣ 分词精度问题**

**困难**：

- 中文文本存在大量未登录词（OOV），导致查询召回率低。
    

**解决方案**：

- 引入 cppjieba，并对词典、停用词进行优化；
    
- 对用户查询和文档内容进行归一化（大小写、全角半角统一），显著降低 OOV 词比例；
    
- 实测前 10 条召回率提升明显。

# 建议补充

## 一、面试时先讲清楚的核心链路

建议把这个项目拆成两条链路讲，面试官会更容易跟上，也更容易追问到你擅长的点。

### 1. 离线链路：文档清洗 + 索引构建

1. 递归遍历 `boostData/rawData` 下的 HTML 文档。
2. 对每个 HTML 提取 `title`、正文文本、原始 URL。
3. 将清洗结果落盘到 `cleanData.txt`，字段之间用 `\3` 分隔，文档之间用 `\n` 分隔。
4. 服务启动时按行读取 `cleanData.txt`，先构建正排索引 `vector<FileInfo>`。
5. 再基于每条正排文档做分词、词频统计，生成倒排索引 `unordered_map<string, InvertedList>`。

一句话版本：

“这个项目本质上是一个离线构建、在线查询的轻量搜索引擎。离线阶段负责把 Boost 文档清洗成结构化文本，在线阶段负责加载索引、分词召回、相关性排序和摘要返回。”

### 2. 在线链路：查询 -> 召回 -> 排序 -> 摘要 -> 返回

1. 前端输入查询词，请求 `/search`。
2. 服务端解析参数，拿到 query。
3. 用 `cppjieba::CutForSearch` 做查询分词。
4. 根据每个分词去倒排索引里召回候选文档。
5. 用 `unordered_map<doc_id, InvertedDedup>` 做去重和权重聚合。
6. 对候选文档按聚合权重排序。
7. 通过 doc_id 回查正排索引，拿到标题、URL、正文。
8. 从正文里截取关键词附近片段生成摘要。
9. 拼成 JSON 返回前端展示。

一句话版本：

“一次查询的核心路径就是：分词召回、聚合去重、相关性排序、正排回表、摘要生成、JSON 返回。”

## 二、建议新增的场景题

### 1. 如果线上搜索突然变慢，你怎么排查？

- 先区分是索引加载慢、分词慢、倒排扫描慢，还是 JSON 返回慢。
- 重点看高频词是否导致倒排链过长，因为当前实现对每个关键词都会扫描整条拉链。
- 再看候选集是否过大，当前实现是全量聚合后排序，候选多时排序成本会明显上升。
- 如果确认是召回阶段慢，可以从高频词裁剪、倒排链压缩、TopK 提前截断入手。

### 2. 如果零结果率突然升高，你会怎么定位？

- 先查数据侧：`cleanData.txt` 是否完整，索引是否构建成功。
- 再查分词侧：查询词是否被切碎、是否出现大量 OOV。
- 再查清洗侧：HTML 提取是否把正文清洗坏了，导致索引里根本没有有效内容。
- 最后查接口侧：是否因为参数名不一致或编码问题导致 query 异常。

### 3. 如果索引构建很慢，你会怎么优化？

- 先拆成三个阶段定位：文件遍历、HTML 清洗、分词建倒排。
- 分词通常是最重的阶段，可以考虑多进程离线构建，再把局部索引做 merge。
- 词频统计可以先做局部 map，再批量写入倒排，减少频繁哈希扩容。
- 可以预估文档量，对 `vector` 和 `unordered_map` 预留容量，减少扩容开销。

### 4. 如果内存占用越来越高，你会怎么解释和优化？

- 当前正排存全文，倒排节点里又保留关键词，存在明显冗余。
- 可以先去掉 `InvertedInfo` 里的 `keyword` 字段，因为 key 已经在哈希表里。
- 再做 doc_id 压缩、权重压缩、倒排链序列化。
- 数据再大时，切到 mmap 或磁盘索引，而不是全量常驻内存。

### 5. 如果面试官问“为什么不用 Elasticsearch”？

- 这个项目目标不是复用工业搜索引擎，而是自己把搜索系统核心链路走一遍。
- 重点价值在于理解离线清洗、索引结构、召回排序、摘要生成和工程取舍。
- 如果直接上 ES，能快速出结果，但很难体现自己对搜索底层机制的理解。

### 6. 如果要支持文档增量更新，你怎么设计？

- 可以把离线构建拆成全量索引和增量索引两层。
- 新文档先进入增量索引，查询时同时查全量和增量，再做 merge。
- 当增量积累到一定规模，再触发后台 merge，生成新的全量索引版本。
- 这样能避免每次文档变更都全量重建。

### 7. 如果要支持短语查询或 AND/OR 查询，你怎么做？

- AND 查询可以取多个倒排链交集，OR 查询可以取并集。
- 真正的短语查询需要位置信息索引，不只是 doc_id 和 weight。
- 当前实现没有保存 term position，所以只能做关键词级召回，不能做精确短语匹配。
- 这个点非常适合当作“下一步优化”来讲。

### 8. 如果高并发下要保证线程安全，你怎么处理？

- 当前索引是启动时一次性构建，查询阶段主要是只读，天然适合多线程并发读。
- 如果后面要支持在线更新索引，就要把读写隔离，例如双 buffer、RCU 或读写锁。
- 单例初始化也要说清楚线程安全策略，避免被追问到并发构建问题。

## 三、建议补充的八股追问

### 1. 为什么正排用 `vector`，倒排用 `unordered_map`？

- 正排按 doc_id 回查，`vector` 连续存储、按下标访问快。
- 倒排按 term 查 posting list，`unordered_map` 更适合按 key 直接定位。

### 2. 为什么要同时保留正排和倒排？

- 倒排负责召回，告诉我“哪些文档包含这个词”。
- 正排负责回表，告诉我“这个文档的标题、URL、正文是什么”。
- 只有倒排很难直接返回完整结果，只有正排又没法高效搜索。

### 3. 召回和排序的区别是什么？

- 召回是尽可能把相关候选找出来，强调覆盖率。
- 排序是把候选按相关性排好，强调前几条结果质量。
- 这个项目里，倒排查询属于召回，权重聚合和降序排序属于排序。

### 4. TF-IDF 和 BM25 你怎么理解？

- 当前项目更像是一个简化版词频权重模型：标题词频和正文词频线性加权。
- TF-IDF 会额外考虑词在整个语料中的区分度。
- BM25 会进一步考虑词频饱和和文档长度归一化，通常比简单加权更稳定。

### 5. 为什么当前项目的相关性模型还比较粗糙？

- 只看了 title/content 词频，没有做 IDF、长度归一化、字段归一化。
- 也没有用户行为特征，比如点击率、停留时长。
- 所以它适合作为教学和面试项目，但距离工业排序还有差距。

### 6. 高词频词为什么会拖慢查询？

- 因为 posting list 很长，召回候选会显著膨胀。
- 当前实现对每个关键词都遍历整条倒排链，再聚合排序，高频词会放大时间和内存开销。

## 四、建议补充的“踩坑和优化”故事

### 1. 数据清洗链路的坑

- HTML 不是结构化文本，直接用状态机去标签虽然简单，但容易把脚本、样式、特殊字符也混进正文。
- 如果 title 缺失、页面格式不规范，清洗阶段就可能失败。
- 这类坑很适合讲成“最开始为了快用了轻量解析，后面发现脏数据会影响索引质量，所以加了容错和统计日志”。

### 2. 索引构建阶段的坑

- 清洗结果如果字段分隔异常，正排构建时就会读到脏行，进而影响倒排。
- 文档量上来后，分词和哈希扩容会成为明显瓶颈。
- 这里可以讲成“我把问题拆成数据正确性和性能两个维度分别处理”。

### 3. 查询阶段的坑

- 多关键词查询不是简单把结果拼起来，而是要去重、聚合、排序。
- 如果不做聚合，用户会看到重复文档；如果不做摘要，结果可读性会很差。

## 八、如果海量数据或超大数据进来，我会怎么处理

这个问题建议你分 3 层回答，不要一上来就只说分布式。

### 1. 第一层：先区分到底是哪种“大”

面试时我会先把“大数据”拆开，因为处理手段不一样：

- **文档总量很大**：从几十万涨到千万、上亿，问题核心是索引体积和查询性能。
- **数据持续高速流入**：新文档不断接入，问题核心是索引更新和在线服务稳定性。
- **单条文档特别大**：比如超长正文、超大 HTML 页面，问题核心是清洗成本、分词成本和摘要生成成本。

一句话可以这样说：

“我会先判断是总量大、流量大，还是单文档大，因为这三类问题分别对应存储扩展、增量更新和单文档治理，不能用一个方案硬套。” 

### 2. 第二层：如果是海量文档持续进来，我的处理措施

#### 方案一：全量索引 + 增量索引

- 线上保留一份稳定的全量索引，保证查询服务可用。
- 新进来的文档先进入增量索引，不直接触碰全量索引。
- 查询时同时查全量和增量，再做结果 merge。
- 当增量达到阈值后，后台异步 merge，生成新版本全量索引，再做原子切换。

为什么这样做：

- 避免每来一批数据就全量重建。
- 避免在线查询和索引更新互相干扰。
- 这是从单机搜索往工程化搜索演进时最常见的方案。

#### 方案二：批处理构建，而不是单条实时重建

- 新数据先写入消息队列或待处理文件。
- 按批次做清洗、分词、建局部倒排索引。
- 最后把多个局部索引做 merge，而不是每条文档都直接改主索引。

这样做的好处：

- 批量处理吞吐更高。
- 更容易做失败重试和脏数据隔离。
- 索引构建成本更稳定，不会把查询线程拖慢。

### 3. 第三层：如果数据大到单机放不下，我会怎么扩展

#### 方案一：先做单机内的压缩和分层

- 去掉倒排节点里的冗余字段，比如 `keyword`。
- doc_id 做压缩存储，weight 做轻量化表示。
- 正排和倒排分离持久化，热点索引放内存，冷数据放磁盘。
- 利用 mmap 或页缓存按需加载，而不是全量常驻。

这一步适合先榨干单机能力，成本最低。

#### 方案二：按 term 或 doc 做分片

- 可以按关键词范围做 term shard。
- 也可以按文档范围做 doc shard。
- 查询时由 broker 把请求打到多个 shard，并把结果聚合回来。

一般我会这样解释：

- **term 分片**更适合倒排索引的组织方式。
- **doc 分片**更适合做数据均衡和水平扩容。
- 具体选哪种，要看写入模型和查询模型。

#### 方案三：查询链路做 TopK 截断

- 当前项目是召回全部候选再排序，数据量大时成本会明显上升。
- 实际上可以在每个 shard 或每个 posting list 上先做局部 TopK。
- 最后只聚合有限个高分候选，而不是全量排序。

这能明显降低 CPU 和内存压力。

### 4. 如果是“超大单文档”进来，我会怎么治理

- 清洗阶段做文档大小阈值控制，超阈值文档单独处理。
- 对正文按段落或块切分，而不是把整篇超长文本一次性分词。
- 建索引时可以只取高价值字段，比如 title、heading、正文前若干 KB。
- 摘要生成时不要在整篇文本上做全量搜索，优先在分块结果里定位命中片段。

这样做的原因：

- 超长文档会拖慢清洗、分词和摘要生成。
- 很多时候后半部分内容对召回贡献不高，但会显著增加成本。

### 5. 如果面试官追问“如何保证在线服务不被拖垮”

我会从隔离、限流、降级三个角度答：

- **隔离**：索引构建和查询服务隔离，避免重建索引抢占在线资源。
- **限流**：对超长查询、超高频查询、高并发请求做限流。
- **降级**：高峰期可以只查热点索引、减少返回条数、关闭复杂排序。

一句话版本：

“海量数据场景下，核心不是让系统永远最优，而是先保证服务不崩，再逐步提升吞吐、召回和排序质量。” 

### 6. 这个项目里我会优先落地的改造顺序

如果要基于你现在这个 Boost 搜索项目继续往下做，我会按下面顺序推进：

1. 先把清洗链路修稳，确保 `cleanData.txt` 完整可靠。
2. 再把索引构建拆成全量索引和增量索引。
3. 给倒排节点做压缩，去掉冗余字段。
4. 支持索引落盘和 mmap 按需加载。
5. 最后再考虑多分片和分布式查询聚合。

### 7. 面试时可直接背的标准回答

“如果海量数据进来，我不会一上来就说上分布式，而是先判断是哪种大。  
如果是数据持续流入，我会用全量索引加增量索引，查询时双路 merge，后台异步做索引合并。  
如果是数据总量大到单机放不下，我会先做倒排压缩、冷热分层、mmap 按需加载，再进一步做分片和 TopK 聚合。  
如果是单文档特别大，我会做分块清洗、分块建索引和摘要截断，避免超长文本拖垮整个链路。  
核心目标是把索引构建和在线查询解耦，保证服务稳定，再逐步提升吞吐和相关性。”

                                                                          # 微服务即时通讯系统 AI 会话与群聊总结：面试官可能追问

## 一、先说结论

基于牛客上的小红书/字节后端面经、简历讨论帖和公开面试流程资料，这段经历如果写在简历上，面试官大概率不会只停留在“你做了什么”，而是会继续深挖下面几类问题：

- 你的项目是不是自己真实做过，还是只会复述功能。
- 这是不是一个“调用大模型 API”的表层项目，还是一个有服务拆分、存储设计、时序控制和异常处理的真实后端项目。
- 你为什么这样设计，而不是用更简单或更常见的方案。
- 你写在简历里的 Redis、MySQL、网关协议、客户端联动，是否都能展开讲清楚。

对大厂后端面试官来说，这段经历的优势不在“用了 AI”，而在“把 AI 能力嵌进了一个微服务 IM 系统，并做了端到端闭环”。

## 二、面试官大概率会怎么拷打

### 1. 先问业务和需求

这是最容易被问的开场。

- 这个 AI 会话和群聊总结，解决的具体用户问题是什么？
- 为什么群聊总结要做成“进入群聊后自动拉取”，而不是手动点按钮？
- 为什么摘要条放在输入框附近，而不是消息流里？
- 为什么设置未读阈值，例如未读达到 5 条才触发？
- AI 单聊和群聊总结的区别是什么？两者为什么都需要？

你要讲清楚：

- 目标用户是谁。
- 典型使用场景是什么。
- 为什么这个触发方式更符合用户路径。
- 你在方案里做了哪些“产品侧约束”，而不是只讲接口实现。

### 2. 然后问整体架构

这段经历最容易被追问的就是服务链路。

- 这套功能的整体链路是什么？
- 请求为什么要先过 gateway？
- gateway、message、ai 服务分别负责什么？
- 客户端在这个链路里承担什么职责，服务端承担什么职责？
- 你为什么没有把所有逻辑都放在一个服务里做？

你要能画出一条完整链路：

- 登录后拉会话列表。
- gateway 聚合会话信息和 unread_count。
- 用户进入群聊后，客户端记录 unread 快照和 snapshot_time。
- message 服务按 Redis 读游标和 MySQL 时间窗裁剪消息。
- ai 服务负责生成纯文本总结。
- 客户端展示摘要条并在合适时机上报已读。

### 3. 紧接着深挖 Redis 和 MySQL

牛客上的后端面经里，Redis 和 MySQL 基本都是高频点，尤其是项目里一旦写了，就很容易被继续追问。

围绕你的项目，大概率会问：

- 为什么读游标放 Redis，而不是直接落 MySQL？
- Redis 的 key 是怎么设计的？
- 为什么读游标要做“只能前进，不能回退”？
- 如果客户端传一个未来时间怎么办？
- 如果 Redis 里没有这个游标，未读数怎么算？
- unread_count 是怎么统计的？SQL 怎么写？
- 为什么摘要只取最近 100 条文本消息？
- 为什么不用 message_id/seq，而先用时间戳？
- 用时间戳有什么边界问题？

这些问题的核心，不是背八股，而是考你能不能把“为什么这样设计”讲得合理。

### 4. 会重点问一致性和时序

这是这段经历最值钱、也最容易拉开差距的地方。

- 为什么群聊总结不能只依赖客户端本地未读数？
- snapshot_time 是干什么的？
- 为什么进入群聊时不能立刻先 mark read？
- 旧请求回包为什么会污染当前状态？你怎么防？
- 如果用户快速切群，或者同一秒多次进入同一群，会不会出问题？
- 为什么客户端要做“本次进入过程”的状态隔离？
- 为什么当前会话收到新消息后，要 debounce 再已读上报？

这部分如果你讲得顺，面试官通常会认为你不是只写接口，而是真的做了闭环。

### 5. 还会问 AI 相关，但不会只问模型

只要简历里出现 AI，大概率会被追问，但问题通常会落到工程化而不是模型原理。

- 你总结接口的 prompt 是怎么设计的？
- 为什么最后要求输出纯文本、200 字以内？
- 如果模型输出 Markdown、结构化列表或者脏格式怎么办？
- 空摘要怎么处理？
- 降级结果怎么处理？
- 为什么不把原始消息全文直接返回给客户端？
- 你怎么判断这个总结结果对用户是“有用”的？

这里不要把重点放到“我会调 API”，而要放到：

- 输入数据是怎么裁剪的。
- 输出格式是怎么约束的。
- 失败和降级是怎么兜底的。
- 为什么这个总结能真正服务用户，而不是只做演示。

### 6. 客户端联动也会被问

因为你简历里写了客户端摘要条与状态联动，这一条很可能会被追问。

- 为什么摘要条不放在消息流里？
- 展开/收起/关闭的状态放在哪一层？
- 为什么关闭只对当前进入过程生效？
- 为什么切会话要隐藏，重新进入再重新评估？
- 为什么摘要展示不应该影响正常聊天输入？
- 你怎么处理旧回包把新会话摘要顶出来的问题？

这类问题其实是在看你是否有“产品闭环意识”。

## 三、针对你简历每一条，面试官最可能问什么

### 1. 参与微服务即时通讯系统开发，负责 AI 会话与群聊未读总结能力落地

大概率追问：

- 你在这个项目里的边界是什么？哪些是你主导做的？
- 你负责的是客户端、服务端，还是端到端？
- 群聊总结的完整工作流你从头到尾讲一遍。
- AI 会话和群聊总结为什么要一起做？

建议准备：

- 明确说出你负责的服务、协议、客户端联动、联调范围。
- 不要泛泛说“参与了”，要能区分“我做了什么”和“团队已有能力是什么”。

### 2. 基于 Redis 读游标与 MySQL 时间窗查询，实现会话未读统计、已读上报与群聊总结接口

大概率追问：

- 为什么读游标选 Redis？
- key 设计是什么？
- unread_count 如何保证口径一致？
- mark read 为什么要做原子推进？
- 为什么用时间窗而不是消息序号？
- 时间窗统计有没有边界问题？

建议准备：

- 讲清楚 Redis 是权威读状态，MySQL 是消息事实表。
- 讲清楚“统计”和“裁剪”分别在哪一层完成。
- 讲清楚这是一个 MVP 方案，为什么先用时间戳，后续为什么可以升级成 message_seq。

### 3. 改造消息服务与网关协议，处理摘要窗口裁剪、空结果返回等问题

大概率追问：

- 为什么 gateway 要参与这个能力，而不是客户端直连 message？
- gateway 聚合了哪些信息？
- 协议里新增了哪些字段？为什么需要 snapshot_time？
- 空结果为什么不能报错，而要正常返回？
- 如果某个下游服务失败了，你怎么降级？

建议准备：

- 讲清楚 gateway 的职责是认证、聚合、统一入口。
- 讲清楚 snapshot_time 的作用是把摘要范围固定在“进入前未读”。
- 讲清楚空结果和失败不是一回事。

### 4. 完成客户端摘要条展示与状态联动，支持自动拉取、展开收起、关闭及已读推进

大概率追问：

- 自动拉取的触发条件是什么？
- 为什么不是进入就一定拉？
- 展开/收起和关闭状态放在哪里？
- 已读推进为什么不能太频繁？
- 你怎么处理摘要和已读上报的时序关系？

建议准备：

- 讲清楚先拉摘要、后 mark read 的原因。
- 讲清楚 debounce 的意义是避免高频无意义请求。
- 讲清楚 UI 位置和交互设计背后的用户考虑。

## 四、面试官最喜欢问的“为什么”

这部分最容易区分“做过”和“看过”。

### 为什么不用客户端本地未读数做权威判断？

标准方向：

- 本地未读只适合做展示，不适合作为服务端权威口径。
- 离线、重登、多端登录都会导致本地状态失真。
- 群聊总结和 unread_count 必须共享同一套权威读状态。

### 为什么要引入 snapshot_time？

标准方向：

- 防止摘要范围被进入群聊后的新消息污染。
- 把总结对象固定成“进入前那批未读”。
- 让客户端展示和服务端裁剪保持同一语义。

### 为什么不能一进入群聊就先 mark read？

标准方向：

- 如果先推进读游标，再去拉摘要，服务端就会认为这些消息已读。
- 摘要窗口会被提前清空，最后只能拿到空结果。
- 所以必须先摘要，再推进已读。

### 为什么只取最近 100 条文本消息？

标准方向：

- 控制 prompt 长度和接口延迟。
- 避免过长上下文稀释关键信息。
- 非文本内容对总结价值有限，先做最有价值的子集。

### 为什么输出纯文本且限制 200 字？

标准方向：

- 群聊总结是辅助信息，不是正文内容。
- 放在聊天界面里，展示成本必须低。
- 200 字更符合摘要条的阅读场景。
- 纯文本更稳定，减少 Markdown、列表、格式错乱带来的展示问题。

## 六、面试官可能继续往下追的延伸题

这些题不是你简历上明写的，但很容易被顺着问出来。

- Redis 持久化机制了解吗？
- Redis 和 MySQL 一致性怎么保证？
- MySQL 索引怎么建？为什么这样建？
- 如果 unread_count 批量查询很多会话，怎么优化？
- 如果 AI 服务变慢或超时怎么办？
- 如果同一个群被频繁进入，摘要缓存要不要做？怎么设计 key？
- 如果未来要支持语音/图片消息总结，方案怎么扩展？
- 如果让你做 AB 实验，你会看哪些指标评估这个功能是否有效？

最后这个 AB 实验问题尤其值得准备，因为它最能体现产品意识。

你可以从这些方向答：

- 摘要曝光率。
- 展开率。
- 用户停留时长。
- 是否减少“爬楼”成本。
- 是否提升群聊回消息效率。
- 是否带来误导或错误总结投诉。

## 七、面试时最容易踩的坑

- 把项目讲成“我接了一个模型接口”。
- 一上来只报技术栈，不讲用户场景和目标。
- 写了 Redis、MySQL、协议、客户端联动，但一问就答不深。
- 说功能做了闭环，却讲不清触发时机和已读时序。
- 为了显得厉害乱写优化指标，但解释不出怎么测的。

## 八、建议你的讲法

建议你用这个顺序回答项目介绍：

1. 先说业务目标：做什么，解决谁的问题。
2. 再说整体方案：服务端怎么裁剪，客户端怎么触发。
3. 再说关键设计：Redis 读游标、snapshot_time、先摘要后已读。
4. 最后说产品意识：为什么这样设计交互，为什么这样做降级和兜底。

如果你一开始就按这个顺序讲，面试官往下追的时候，你会稳很多。

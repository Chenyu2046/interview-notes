# 微服务 IM：AI 会话与群聊未读总结问题清单

## A. 第一层：先把业务讲明白

### 业务链路
#### 你先完整讲一下这个 AI 会话 / 群聊未读总结的业务链路。
**AI 会话**本质上是把 AI 做成一个特殊的聊天对象，用户可以像发普通消息一样给它发消息。整体链路是，用户发消息后，系统先按正常聊天消息处理，把用户输入纳入原有消息链路，然后异步调用 AI 生成回复。AI 回复生成后，再以普通消息的形态回到消息系统里，这样前端看到的就是一个真实会话，而不是单独拼出来的问答窗口。这样做的好处是复用了原有消息链路，持久化、展示、推送逻辑都不用单独造一套。”

“**群聊未读消息总结**是另一条链路。具体场景是：用户重新进入群聊时，系统帮用户快速理解这段时间错过了什么。整体逻辑是，客户端进入群聊时会触发一次摘要请求，服务端先确认当前用户确实有权限看这个群，然后根据他退出群聊之前最后已读位置和重新进入时刻，裁出一段真实的未读消息窗口。这个窗口里只取需要总结的文本消息，不会把所有历史消息都扔给模型。之后服务端会先查缓存，如果之前同一批未读消息已经总结过，就直接复用；如果没有命中，再调用模型生成摘要。最后客户端把摘要展示在聊天输入框上方，帮助用户快速扫一眼重点。等用户真正看完这批消息后，再推进已读状态。”


#### 服务端收到请求后依次经过哪些服务？
服务端收到请求后，第一层先做统一接入和身份校验，确认请求是合法用户发起的；
第二层进入消息域逻辑，去判断这个会话是不是群聊、这个用户是不是群成员，然后结合用户当前的已读位置和本次进入时刻，裁出真实未读窗口；
接着会对这段窗口做一次消息过滤，只保留需要参与总结的文本消息。如果这批消息之前已经总结过，就直接命中缓存返回；如果没有命中，再去调用 AI 能力生成摘要。AI 生成完成后，结果再返回给消息服务封装，最后由网关返回给客户端展示。
整个链路里，网关负责接入和鉴权，消息服务负责未读窗口计算、过滤、缓存和结果组装，AI 服务只负责根据输入生成摘要。”


#### 群聊未读总结和 AI 会话，本质差别是什么？
AI 会话是在解决‘用户现在想问什么’，群聊未读总结是在解决‘用户刚回来时需要先补什么’。一个是实时对话，一个是未读信息压缩。”

### 触发定义
#### 你们怎么定义“用户需要摘要”这件事？触发门槛是什么？
#### 摘要是实时生成还是缓存复用？命中率大概多少？
用户进入群聊后，服务端先看读游标和本次进入时刻之间有没有真实未读窗口。  
如果没有未读，就直接返回‘无需摘要’；  
如果有未读，再看这个未读窗口是不是已经生成过摘要。窗口完全一致就复用缓存，不一致就实时生成。


>**缓存复用命中率：**
>
这个缓存的命中率不会特别高，因为用户一旦正常读完，读游标就推进了，后面再次进入群聊通常是‘没有未读，不触发摘要’，而不是‘命中旧缓存’。  
所以缓存真正命中的场景，主要是同一未读快照下的短时间重复进入、前端重试、并发请求，或者已读还没来得及上报前的重复拉取。  
从这个业务形态看，它更像一个**短期去重缓存**，命中率通常是低到中等，不会像静态内容缓存那么高
#### 如果一个群聊 10 万条未读消息，你怎么避免直接把模型打爆？
先通过已读位置裁出真实未读窗口，再过滤文本消息，并限制最大输入规模。大部分请求会在这一层就被压到可控范围内。只有在过滤后仍然过长时，我才会考虑分段摘要，把每段先压缩，再对各段摘要做一次汇总。


## B. 第二层：追着你的指标问

### Bullet：优化已读游标与时间窗查询，将 MySQL 查询控制在 20~30ms，消息链路延迟保持在 300ms 以内。
#### 1. 你怎么优化已读游标和时间窗查询的

"核心思路是两步：把未读状态判断前移，把消息查询压缩成小范围定界查询。

已读游标这边，不在消息表里现算用户读到哪里，而是给每个用户每个会话维护一个游标，记录已读到的时间点。用户进群时直接读游标，不扫消息表。游标只前进不回退，避免并发更新把状态算乱。

有了游标之后，未读范围就收缩成一个明确的时间窗——游标之后到本次进入时刻之前。查询从全量历史扫描变成会话+时间窗的范围查询。在这个基础上再做几层收缩：只查当前会话、只查真实未读窗口、排除自己发的消息、摘要只保留文本、再加 limit 限制拉取量。数据库看到的始终是一个受控的小查询。

#### 2. 你怎么将 MySQL 查询控制在 20~30ms 中的？你怎么测出来的？
怎么做到的：四件事。先读游标，很多请求在这步直接判断没有真实未读，根本不打后续查询。一旦要查消息，也只按会话+时间窗查未读区间，数据量天然受控。查询条件再收紧，带会话、时间、消息类型、排除本人、加 limit，避免拉出无关数据。索引侧围绕 session_id、create_time 设计联合索引，必要时加 message_type，否则遇到活跃大群耗时口径是不稳的。

怎么测出来的：日志埋点加重复压测采样，不是单次观察值。做法是在消息查询前后单独打时间点，只记数据库查询耗时，不把鉴权和模型调用混进去。针对低、中、高不同未读量场景多次采样，看平均值和分位值。同时配合慢 SQL 日志和 explain 验证查询计划。

所以我说 20~30ms，指的是已读游标确定窗口后、这类未读消息查询在目标场景下的单次查询耗时，不是整个摘要接口耗时，也不是说数据库永远稳定在这个数。"

#### 3. 你怎么做到消息链路延迟保持在 300ms 以内的？你怎么测出来的？
"先纠偏一下：这里的 300ms 指的是普通消息主链路延迟，不包含 AI 摘要或 LLM 调用。只要进模型，300ms 这个口径通常就不成立了，所以我会把两条链路拆开讲。

怎么做到的：核心是主链路和 AI 链路解耦。普通消息发送只走接入、校验、持久化、投递这条轻链路，优先保证消息本身尽快落下去、对端尽快可见。AI 能力，比如摘要生成、模型回复，全部走独立的异步链路，不阻塞主路径。模型是附加能力，不是消息发送成功的前置条件。这样 AI 的不稳定耗时就不会拖垮普通消息体验。

怎么测出来的：每条请求进来时生成一个 request_id，这个 ID 贯穿整条主链路。然后在几个关键节点各打一个时间戳：请求到达服务端、完成鉴权校验、消息写入存储、对端确认可见。最后按 request_id 把这几条日志聚合，就能算出主链路总耗时，也能拆出每一段谁最慢。压测时在固定并发和消息体大小下多轮采样，看平均值和 P95，不看单次最好结果。

所以 300ms 以内不是靠某一个点提速，而是靠链路分层加定点打点。主链路只做必要的事，AI 走异步，测量上用 request_id 串联关键节点，主链路延迟和 AI 耗时不会互相污染。"

### 优化收益证明
#### Bullet：通过摘要缓存与 Prompt 裁剪，减少 30%~50% 的冗余 AI 调用，摘要响应时间控制在 1.2s~1.8s。
##### 摘要缓存和 Prompt 裁剪你是怎么做的？
摘要缓存和 Prompt 裁剪我分成两层做。摘要缓存主要解决的是同一批未读消息不要重复打模型，所以我不是按群聊粗暴缓存，而是按用户、会话和未读窗口快照来复用。服务端会先根据已读游标和本次进入群聊的时刻，确定一个真实未读窗口，只有窗口完全一致时才命中缓存；如果来了新消息或者已读位置前进了，就视为新窗口，重新生成摘要。这样做主要是减少重复 LLM 调用，尤其是短时间重复进入、前端重试和并发请求场景。

Prompt 裁剪主要解决的是单次调用不要把输入做得过大。我会先裁消息集合，只保留真实未读窗口里的有效文本消息，排除自己发的、空内容和非文本消息，再加条数上限；然后对超长单条消息做截断；最后再按总字符数或者 token 预算控制整个 prompt 大小，优先保留更靠近当前时刻的消息。这样既能保证摘要还原主要上下文，又能把单次模型调用的耗时和成本控制在可接受范围内。


- 30%~50% 冗余 AI 调用减少，是怎么统计的？AB 对照了吗？
##### Prompt 裁剪裁了哪些内容？为什么不会明显影响摘要质量？
`目前 只是总结全部文本信息，后续优化如下`
第一步，我会先做轻量清洗，把空内容、纯表情、重复碎片这种噪声先去掉；如果同一个人连续发很多很短的文本，我会合并，避免模型把大量 token 浪费在低价值内容上。

第二步，我不会只按时间硬截，而是优先保留两类信息：一类是最近的消息，因为和用户当前最关心的上下文最相关；另一类是信息密度高的消息，比如明确的结论、分工、待办、时间点、争议点。这样即使输入要裁剪，我留下来的也更像摘要素材。

第三步，如果内容还是很长，我会做分段摘要。先把消息按 token 预算拆成几段，让模型先对每段产出中间摘要，再把这些中间摘要汇总成最终摘要。这样比直接丢掉前半段更稳，因为早期内容没有完全丢，只是被压缩了一层。

最后在 prompt 上，我也不会只让模型“自由总结”，而是明确要求它提取讨论主题、已确认结论、待办事项和未解决问题。这样输出会更稳定，也更接近用户真正需要的信息。

所以一句话说，我是通过“清洗降噪 + 优先级裁剪 + 分段摘要汇总”来保证长文本场景下摘要质量不会明显下降。

## C. 第三层：已读游标 / 时间窗 / MySQL 索引设计

### 读游标设计
#### 已读游标是什么结构？按用户维度存，还是按会话维度存？
已读游标不是单独按用户存，也不是单独按会话存，而是按 **用户和会话的二元关系** 存，也就是 (user_id, chat_session_id) 这一维。

原因很简单：

- 同一个用户会有很多会话，每个会话的已读进度不一样
- 同一个会话里也有很多用户，每个人的已读进度也不一样
- 所以它本质上是一个“会话成员状态”，最合理的建模就是 user + session

我这里用的结构比较轻：

- key：chat_read_cursor:{user_id}:{chat_session_id}
- value：last_read_time 或者说 read_up_to_time

也就是说，当前存的不是未读数，而是“这个用户在这个会话里读到了哪个时间点”。有了这个值之后，服务端就可以用 (last_read_time, snapshot_time] 这样的时间窗去算真实未读范围。

更新策略上，我做的是**只前进不回退**。如果客户端重复上报或者乱序上报，只有新的时间比旧的更大时才覆盖，这样能避免旧请求把新状态冲掉。


#### 已读游标更新和消息写入并发时，会不会算错未读数？
会有并发风险，但我这里的处理思路是：**不追求“绝对瞬时一致”，而是保证“游标单调前进 + 未读窗口最终收敛正确”**。

先说为什么会有这个问题。  
消息写入和已读上报本来就是两条独立链路：

- 一条是新消息进来，进入转发、MQ、持久化
- 一条是用户看完后，上报自己读到了哪个时间点

这两条链路并发时，确实可能出现边界抖动，比如：

- 用户刚上报已读
- 同时有一条新消息刚写进来
- 那这条消息到底算已读还是未读，取决于它的时间戳和已读时间点的先后关系

我的处理方式有两个核心点。

第一，**已读游标只前进不回退**。  
也就是说，读状态更新不会因为乱序请求倒退，这样至少不会出现“已经读过的内容突然又变未读”的明显错误。

第二，**未读数和摘要窗口都按明确边界计算**。  
比如我这里不是直接存未读数，而是存 read_up_to_time，然后在查询时按：

- create_time > last_read_time  
    去算未读，  
    或者在摘要场景下按：
- (last_read_time, snapshot_time]  
    去裁窗口。

这样就把问题变成了“边界归属问题”，而不是全局状态混乱问题。即使在并发点上有一两条消息落在边界附近，影响也只是那一瞬间某条消息归到已读还是未读，不会把整个未读体系算乱。

如果面试官继续追问，我会补一句：

“所以严格说，它可能在极短时间窗口里出现边界抖动，但不会出现状态回退和长期错误。这个场景下我更关心的是最终一致性和用户感知稳定性，而不是为了追求绝对瞬时一致去把主链路做得特别重。”
- 如果消息乱序到达、补写历史消息，摘要时间窗怎么保证正确？

### 未读计算
#### 群聊未读消息是怎么计算的？为什么不用每次 `count(*)` 全表扫？
群聊未读数我不是直接存一个未读值，而是基于已读游标现算。服务端会先拿到用户在这个会话里的 `last_read_time`，然后统计这个会话中该时间点之后、且不是本人发送的消息数。这样做的关键是，查询只落在“这个会话 + 已读边界之后”这一小段范围内，而不是每次对整个群历史做 `count(*)` 全表扫描。这样成本更稳定，也能和后面的摘要时间窗裁剪复用同一套边界。

#### 时间窗查询的 SQL 长什么样？`where` 条件是什么？
“当前实现里，时间窗查询不是泛泛地查最近消息，而是有一组比较明确的 where 条件。  
如果是群聊未读摘要，服务端会先拿到用户在这个会话里的 last_read_time，以及本次进入群聊时记录的 snapshot_time，然后查这两个时间点之间的消息。具体条件是：

- session_id = 当前会话
- create_time > last_read_time
- create_time <= snapshot_time
- user_id != 当前用户
- message_type = STRING
- 再加 order by create_time desc limit N

也就是说，摘要不是查整个群历史，而是查当前用户这次真实未读窗口内、别人发的、文本类型的消息，再从里面取最近一批候选消息做总结。

如果是未读数统计，条件会更简单一些，核心就是：

- session_id = 当前会话
- create_time > last_read_time
- user_id != 当前用户

所以本质上，无论是未读数还是未读摘要，底层都是基于同一个已读边界去做范围查询。区别只是摘要场景会额外加消息类型过滤和 limit，用来控制输入规模和总结范围。”

### 索引与存储
#### 你的索引是怎么建的？联合索引字段顺序为什么这么排？
严格按当前代码来说，库里现有索引还比较基础，message 表是 message_id 唯一索引和 session_id 索引，chat_session_member 表是 session_id 索引。真正要把未读时间窗查询做稳，我会补 message(session_id, create_time) 这样的联合索引，摘要场景再评估是否扩成 message(session_id, create_time, message_type)。字段顺序上，session_id 放最左是因为查询总是先锁定某个会话，再在会话内按时间窗做范围过滤；create_time 放第二是为了直接服务 last_read_time -> snapshot_time 这类范围查询；message_type 是否纳入则取决于摘要查询占比和过滤收益。”
#### 什么情况下索引会失效？
索引失效通常有几类：一是对索引列做函数、计算或隐式类型转换；二是联合索引没有命中最左前缀；三是范围查询之后还希望高效利用后续列；四是条件选择性太差，优化器觉得全表扫更便宜。比如我这个场景如果建的是 session_id, create_time，那正常应该先按 session_id 等值过滤，再按 create_time 做时间窗范围查询；如果只按 create_time 查，或者对 create_time 做函数处理，索引效果就会明显变差。”


#### 如果群消息表数据越来越大，你后面准备怎么拆？分表？冷热分层？
我会分阶段做，不会一上来就直接分库分表。

第一阶段，先把单表查询路径压到最优。因为我这个场景大部分查询其实都是按 session_id + 已读边界 + 时间窗 去查一小段数据，不是扫全表，所以先把已读游标、时间窗范围查询和联合索引做好，单表还能撑一段时间。

第二阶段，我会优先做冷热分层。IM 里真正高频访问的通常是最近消息、最近未读和最近摘要窗口，老消息更多是长尾查询，所以我会把近期热数据和历史冷数据拆开。这样能先把高频路径的表控制得更轻，收益通常比直接分表更平滑。

第三阶段，如果数据量和写入压力继续涨，再按 session_id 维度做分表或分片。因为这个场景无论拉历史、算未读还是做摘要，核心访问维度都是会话，所以按会话路由最自然。

所以我的顺序是：**先优化查询路径，再冷热分层，最后按会话维度分表**。这样改动成本和收益比更合理。

## D. 第四层：缓存、降级、异常兜底

### 缓存设计
#### 摘要缓存的 key 怎么设计？按用户、群、时间窗、游标版本怎么编码？
我会把摘要缓存 key 设计成**能唯一标识这次未读窗口**的组合，而不是只按群或者只按用户粗暴缓存。

核心维度我会放这几个：

- `user_id`：同一个群里不同用户的未读范围不一样
- `chat_session_id`：区分不同会话
- `last_read_time` 或读游标版本：表示这次未读窗口的起点
- `snapshot_time`：表示这次摘要窗口的终点，也就是用户进入群聊时刻
- `summary_limit` / 输入上限参数：因为它会影响最终摘要结果

也就是说，缓存语义不是“这个群的摘要”，而是“这个用户在这个群、这段未读窗口上的摘要结果”。

如果写成一个示意 key，大概会是：

```text
unread_summary:{user_id}:{chat_session_id}:{last_read_time}:{snapshot_time}:{limit}
```

这样编码的原因是：

1. `user + 群` 决定是谁在看哪段消息  
2. `last_read_time + snapshot_time` 决定这次未读窗口边界  
3. `limit` 决定 prompt 输入规模，属于结果版本的一部分

所以只有当这几个维度都一样时，我才认为可以直接复用缓存；只要来了新消息、已读位置前进了，或者输入裁剪参数变了，就视为新窗口，不复用旧摘要。


#### 缓存什么时候失效？新消息来了立刻失效，还是基于版本号？
我不会做“新消息一来就主动删缓存”这种强失效，而是更偏向**基于窗口版本自然失效**。

原因是这个摘要缓存本身不是“群的最新摘要”，而是“某个用户在某个群、某个未读窗口下的摘要结果”。只要窗口边界变了，这个 key 就天然变了，旧缓存就不会再命中。所以新消息来了，不一定要主动去删；因为新消息会让 snapshot_time 变化，或者后面已读游标推进了，last_read_time 也会变化，最终都会形成新的缓存 key。

另外我还会给缓存加一个比较短的 TTL，让旧窗口结果自动过期。这样做的好处是：

- 不用维护复杂的主动失效逻辑
- 不需要广播删除缓存
- 语义更稳定，因为窗口不一致时本来就不该复用

所以如果面试官问我，我会回答：  
**主策略是基于窗口版本自然失效，辅以短 TTL 回收，而不是新消息一来就全量主动删缓存。**

#### 为什么不用永久缓存？
因为这个摘要结果本质上是**某个用户在某个时刻的一段未读窗口视图**，不是稳定业务主数据，所以没有必要永久缓存。

第一，窗口是强时态的。  
只要新消息来了，或者用户已读位置变了，这个摘要对应的上下文就变了，旧结果很快就失去复用价值。永久缓存会堆积大量几乎不会再命中的旧窗口。

第二，缓存目标是**去重和削峰**，不是长期存档。  
它主要解决的是短时间重复进入、前端重试、并发请求这种场景，所以短 TTL 已经够用了，没必要把所有历史摘要都长期保留。

第三，永久缓存会带来额外成本。  
包括内存占用、清理策略、版本管理和一致性复杂度。对于这种时效性很强的辅助结果，长期持有的收益很低。

所以我会把它定义成一个**短期窗口缓存**，而不是长期资产缓存。简单说，就是它的目标是挡住短时间重复调用，不是保存一份永久摘要档案。


#### 缓存和数据库、模型结果之间怎么保证一致性？
我不会把这里的一致性目标定义成“强一致”，而是定义成**窗口语义一致**。

因为这个摘要缓存不是主数据，它只是某个未读窗口上的派生结果。所以我真正要保证的是：**缓存命中时，它对应的窗口边界必须和当前请求完全一致。**

具体做法有两层：

第一层是**key 设计保证语义一致**。  
缓存 key 里会带上 `user_id`、`chat_session_id`、`last_read_time`、`snapshot_time` 这些窗口边界信息。只有当前请求和历史请求的未读窗口完全一样，才允许命中缓存。这样就不会出现“数据库里的未读范围已经变了，但还拿旧摘要硬返回”的问题。

第二层是**数据库负责事实，缓存只负责复用结果**。  
数据库和 Redis 里的读游标决定这次真实未读窗口是什么，模型只是针对这个窗口生成摘要，缓存只是把这个生成结果短时间保存下来。所以顺序上始终是：
1. 先根据状态算窗口
2. 再决定是否命中缓存
3. 未命中才调用模型
4. 把结果按当前窗口写缓存

也就是说，缓存从来不反过来定义业务状态，它只复用一个已经有明确窗口边界的结果。

所以我会这样总结：
**不是去保证缓存和数据库逐字段强一致，而是保证缓存结果和当前未读窗口的一致性。数据库负责真实状态，模型负责生成，缓存只在窗口完全相同时复用结果。**


### 失败与降级
- ==AI 服务超时了怎么办？失败重试还是直接降级？==
- ==空摘要返回的定义是什么？和失败返回怎么区分？==
- ==如果模型服务偶发抖动，怎么避免把上游线程池拖死？==
- ==你们有没有做限流、熔断、隔离舱？==
`“按现在这版代码，AI 服务超时不是直接无限重试，而是**有限重试，失败后降级**。  
具体实现上，ai service 里无论是 ChatWithAI 还是 UnreadMessageSummaryWithAI，都会先调用 _llm_client->chat(...)，如果失败且错误码属于可重试类型，只会按配置做有限次重试；可重试错误在代码里只有两类：RetryableError 和 NetworkError。重试之间还会做指数退避加抖动。  
真正的超时是在 LLMClient 里通过 cpr::Session::SetTimeout(config_.timeout_ms) 控制的，当前默认 flag 是 60000ms。如果最终还是失败，AI 会话会返回固定兜底文案，群聊摘要会返回固定兜底摘要，并把 is_degraded 标成 true。”

“空摘要和失败，在代码里是明确区分的。  
空摘要属于**业务上无需生成**，比如两种情况：

1. last_read_time >= snapshot_time，说明没有真实未读窗口；
2. 过滤后的文本消息数低于最小阈值。  
    这两种情况下，message service 都是直接 response->set_success(true) 返回，不会去调 AI。  
    失败则是另外一类：比如 prompt 构建失败、拿不到 AI service channel、brpc 调用失败，或者最终摘要内容为空，这些都会走 err_response，返回 success=false。  
    还有第三种状态叫**降级成功**：如果 AI 服务本身调用 LLM 失败，但 fallback 摘要文案非空，ai service 会返回 success=true、is_degraded=true，上层 message service 最终也会按成功返回，只是把 degraded 标出来。”

“如果模型服务偶发抖动，当前代码里真正已经做掉的保护手段有两个。  
第一，AI 会话那条链路在 gateway 里是单独起了一个 std::thread(...).detach() 去调 AIService.ChatWithAI，代码注释也明确写了‘防止 AI 耗时影响响应顺序’，所以它不会阻塞用户发消息这条主响应。  
第二，LLM 调用本身有超时和有限重试，不会在 ai service 里无限挂着。  
但如果严格按代码说，**并没有看到专门的线程池隔离、任务队列隔离或者 bulkhead 实现**。尤其群聊摘要这条链路还是 gateway -> message -> ai 的同步 RPC 调用，所以这部分只能说有超时和重试控制，但没有做得很重的隔离治理。”

“限流、熔断、隔离舱这几块，如果只看当前代码，我不能说已经做了。  
我看到的只有：

- brpc channel 层统一 max_retry = 3
- LLM HTTP 请求有 timeout_ms
- AI service 内部有基于错误码的有限重试和 backoff
- 失败后有 fallback / degraded 语义`

### 状态语义
- 你有没有分清“失败”“超时”“无内容可摘要”“命中旧缓存”这几类状态？
- 你有没有做幂等、重试边界、超时控制？
> 有区分，但不是全部做成独立状态码。无内容可摘要 和 命中旧缓存 都是在 message service 里直接返回 success=true；前者表示没有真实未读窗口或者文本不足阈值，后者表示同一未读窗口命中了缓存。失败 和 超时 主要在 ai service/LLMClient 里处理，超时会被归到 NetworkError，属于可重试失败；最终失败时会走 fallback 和 is_degraded，如果上游链路本身失败则返回 success=false。幂等方面，当前最明确的是已读游标用 set_if_greater 保证只前进不回退，摘要缓存也避免了同窗重复调用；重试边界和超时控制则主要通过 timeout_ms、max_retries 和退避策略来实现。”

## E. 第五层：微服务理解，不会只问概念

### 微服务边界
- 你理解的微服务是什么？不是定义，是结合你这个项目说。
- 为什么这个摘要能力不做在原服务里，要拆成独立服务？
- 你这个场景里，微服务带来的收益和成本分别是什么？
> “如果结合我这个项目来讲，我理解的微服务不是简单把代码拆成几个进程，而是**按领域职责拆边界，让不同服务分别拥有自己的核心状态和处理逻辑**。  
比如我这个 IM 项目里，friend service 管会话和成员关系，message service 管消息存储、未读数和已读游标，transmit service 管发消息时的目标计算和消息对象组装，ai service 只管调用模型生成回复或摘要。gateway 则是统一入口和编排层。  
所以微服务在这个项目里的意义，不是‘为了拆而拆’，而是让每个服务只处理自己最相关的那部分问题。”

>“为什么摘要能力不直接塞进原服务，而是拆到独立 AI 服务，我觉得有两个核心原因。  
第一，摘要生成本质上是**模型调用能力**，它和会话关系、消息存储不是同一种职责。消息服务最擅长的是算清楚未读窗口、过滤消息、构造 prompt；但真正去跟 LLM 打交道，做超时、重试、退避、fallback，这更适合放在独立 AI 服务里。  
第二，AI 能力的耗时和稳定性跟普通业务服务不一样。如果把模型调用直接揉进消息服务或者网关主逻辑里，很容易把原本比较稳定的消息链路拖慢。拆出来之后，至少在边界上能把‘状态计算’和‘生成调用’分开。”

> “在我这个场景里，微服务带来的收益很明确。  
第一是职责清晰。像群聊未读摘要这条链路里，message service 只需要负责窗口裁剪和缓存，ai service 只负责生成，边界比较干净。  
第二是复用性好。AI 会话和群聊未读摘要两条能力，虽然业务不同，但最后都能复用同一个 AI 服务和同一个 LLM 客户端。  
第三是主链路更容易保护。比如 AI 会话里，用户消息还是走正常消息链路，AI 回复是独立异步去生成，不会直接阻塞用户发消息这条主路径。”

> “但成本也很现实。  
第一是调用链变长了，请求经常要跨 gateway、message、ai 多个服务，排障和 tracing 都更复杂。  
第二是状态分散了，像会话关系、消息存储、已读游标、摘要缓存分别落在不同地方，做一个完整功能时经常要跨服务编排。  
第三是异常处理会更麻烦。一个摘要请求失败，到底是网关、消息服务、AI 服务还是 LLM 下游的问题，不像单体应用那么直观。  
所以我会认为，微服务在这个项目里确实带来了边界清晰和演进灵活性，但同时也增加了调用链复杂度和治理成本。”

### 服务间通信
- 服务之间怎么通信？HTTP、RPC、MQ？为什么？
- 跨服务调用链路长了以后，超时怎么设置？
- 一个请求跨多个服务，怎么做 tracing？

> 可以这么答，而且我会严格按当前代码讲。

“这个项目里，服务之间不是只用一种通信方式，而是**按场景混用**。  
对外入口主要是 `HTTP + WebSocket`：客户端请求先打到 `gateway` 的 HTTP 接口，像发消息、拉会话列表、拉未读摘要都是 HTTP；服务端往在线用户推新消息、AI 回复这类实时通知，用的是 WebSocket。  
服务内部的同步调用主要是 `brpc + protobuf`，比如 `gateway` 调 `friend`、`message`、`transmit`、`ai`，以及 `message` 再调 `ai`。  
异步链路则用 `RabbitMQ`，最典型的是普通消息发送和 AI 回复持久化：先发到 MQ，再由 `message service` 消费入库。  
`MySQL` 和 `Redis` 不是服务间通信协议，但它们是这条流程里的关键状态层：MySQL 存用户、会话、成员、消息；Redis 存 session 和已读游标这类高频状态。”

“为什么这么分？因为场景不一样。  
HTTP 适合客户端接入，WebSocket 适合实时下行推送，RPC 适合同步、强结构化的内部服务调用，MQ 适合把消息生产和持久化解耦，避免主链路被存储拖住。  
所以不是为了技术栈丰富而混用，而是每种方式各自解决不同问题。”

“如果把这些东西放到一条典型流程里看，可以这样理解：

1. **普通消息发送**  
客户端先通过 HTTP 打到 `gateway`；  
`gateway` 再通过 RPC 调 `transmit service` 算转发目标、组装消息；  
`transmit` 把消息发到 RabbitMQ；  
`message service` 消费 MQ 后写 MySQL；  
同时 `gateway` 通过 WebSocket 把新消息推给在线用户。  
这一条里：
- HTTP 是入口
- RPC 是同步业务编排
- MQ 是异步持久化边界
- MySQL 是最终事实存储
- WebSocket 是实时通知

2. **群聊未读摘要**  
客户端通过 HTTP 请求 `gateway`；  
`gateway` 通过 RPC 调 `message service`；  
`message service` 先读 Redis 里的已读游标，再查 MySQL 时间窗消息；  
如果需要生成摘要，再通过 RPC 调 `ai service`；  
`ai service` 再通过 HTTP 调外部 LLM；  
最后结果原路返回。  
这一条里：
- Redis 负责快速状态判断
- MySQL 负责真实消息窗口
- RPC 负责服务间同步编排
- 外部 HTTP 是 AI 下游模型调用”

“超时这块，如果严格按当前代码讲，内部 brpc channel 用的是统一默认配置，`connect_timeout_ms = -1`、`timeout_ms = -1`、`max_retry = 3`，也就是说内部 RPC 没有在每个调用点上精细拆超时预算，而是用了比较宽松的统一配置。  
LLM 下游这层则有明确超时，`LLMClient` 里 `cpr::Session::SetTimeout(config_.timeout_ms)`，当前 AI 服务默认 flag 是 `60000ms`。  
所以如果问‘跨服务链路长了以后超时怎么设置’，严格按代码说，当前实现并没有做得特别细，更多是：
- 内部 RPC 用统一 brpc 配置
- LLM HTTP 调用单独设超时
- AI 服务内部再加有限重试和退避  
如果我要往生产化继续收，我会进一步拆总预算，比如 gateway 到 message、message 到 ai、ai 到 LLM 各自单独限时，但这一步当前代码里还没有完整做到。”

“Tracing 这块也要实话实说。  
当前代码里没有看到完整的分布式 tracing 系统，比如 Jaeger、SkyWalking 或 OpenTelemetry。  
现在更接近**轻量 request_id tracing**：请求从网关进来后会带 `request_id`，服务间 protobuf 请求会把这个 `request_id` 往下透传，然后各层日志都打这个 ID。  
所以它能支持链路排查，但还不是完整的分布式观测体系。  
也就是说，现在做到的是‘日志级关联追踪’，不是‘标准 tracing 平台’。”

你放到逐字稿里可以用这版：

“这个项目里通信方式是按场景混用的：客户端到网关主要是 HTTP，请求下发和实时通知用 WebSocket；服务内部同步调用主要是 brpc + protobuf；消息持久化这种异步边界用 RabbitMQ；MySQL 存事实数据，Redis 存 session 和已读游标这类高频状态。比如普通消息发送是 HTTP 进网关，RPC 到 transmit，消息发到 MQ，message service 消费后写 MySQL，网关再通过 WebSocket 推给在线用户；群聊未读摘要则是 HTTP 到网关，RPC 到 message，message 先读 Redis、查 MySQL，再 RPC 调 ai，ai 再通过 HTTP 调外部 LLM。超时上，当前代码里内部 brpc 还是统一配置，没有拆得很细，LLM HTTP 调用单独有 timeout 和有限重试。Tracing 方面，目前主要靠 request_id 在各服务日志里透传，还没有完整的分布式 tracing 平台。”

### 稳定性与自保
- 服务雪崩怎么防？
- 如果下游 AI 服务慢，你这个摘要服务该怎么自保？
>严格按当前代码说，防雪崩主要靠三件事：一是 AI 会话里把 AI 回复生成和主消息响应解耦，避免阻塞主链路；二是 AI service 到 LLM 的调用有 timeout、有限重试和退避；三是失败后可以走 fallback 或 degraded，不把模型不可用放大成主流程失败。但我没有看到完整的熔断、限流和隔离舱，所以这还不是完整的雪崩治理。对于群聊摘要，如果下游 AI 服务慢，当前的自保主要是超时、重试边界、降级和同窗缓存；但因为 message 到 ai 还是同步调用，没有专门线程池隔离，所以真正要做强还得补隔离、熔断和限流。”

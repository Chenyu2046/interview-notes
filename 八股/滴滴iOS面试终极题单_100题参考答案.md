## 一、内存管理

### 1. ARC 的工作原理是什么？

结论：ARC 本质上是编译器帮我们在合适的位置自动插入 retain、release 和 autorelease，不是运行时全自动魔法。比如一个对象被属性强持有时计数加一，离开作用域又没人持有就释放。坑是 ARC 只能管 OC/Swift 对象，Core Foundation 这类还得手动处理桥接。

### 2. strong、weak、unowned 的区别？

结论：strong 是持有对象，weak 不持有且对象释放后会自动置 nil，unowned 也不持有但默认对象一定还活着。比如父控制器持有子对象一般用 strong，delegate 常用 weak。坑是 unowned 一旦对象先释放，再访问就会直接崩。

### 3. weak 为什么不会产生野指针？

结论：因为 weak 底层会被放进一张弱引用表，对象销毁时运行时会把所有指向它的 weak 引用统一清成 nil。就像通讯录里有人注销了，系统把所有快捷联系人一起删掉。注意这也是 weak 访问比普通强引用稍微慢一点的原因。

### 4. 循环引用有哪些常见场景？

结论：最常见就是两边互相强持有，比如 controller 持有 viewModel，viewModel 里的闭包又强抓 controller；还有 Timer、delegate 写错成 strong。就像两个人互相拉着手，谁都走不掉。面试里最好顺手说出用 weak、拆闭包、手动 invalidate 这些解法。

### 5. 闭包为什么容易造成循环引用？

结论：因为闭包本身是引用类型，被对象持有后，闭包里如果又强引用这个对象，就形成环了。比如 self 持有一个网络回调 block，block 里面直接用 self 更新 UI。坑是异步闭包和长期保存的闭包最危险，临时闭包问题反而没那么大。

### 6. [weak self] 和 [unowned self] 的区别？

结论：weak self 更安全，适合对象可能提前释放的异步场景；unowned self 更省一次可选解包，但前提是 self 生命周期一定覆盖闭包。比如网络请求回调我一般用 weak self，初始化时短生命周期绑定才考虑 unowned。坑是为了省代码乱用 unowned，线上很容易出崩溃。

### 7. autoreleasepool 的作用是什么？适合哪些场景？

结论：它是给临时对象一个延迟释放的池子，池子排空时统一回收，适合大量临时对象的循环场景。比如批量图片处理、文件遍历时每轮包一层 autoreleasepool，可以明显压低峰值内存。坑是以为 ARC 下就完全不用关心 autorelease，这个想法不对。

### 8. Timer / CADisplayLink 为什么容易造成循环引用？

结论：因为它们会强持有 target，如果 target 又强持有 timer，就形成环了。常见场景就是控制器里开一个 Timer 刷 UI，页面退出了却没释放。解决一般是中间代理、block 版加 weak self，或者在 deinit、viewDidDisappear 里及时 invalidate。

### 9. Swift 的值类型和引用类型在内存管理上有什么区别？

结论：值类型更强调拷贝语义，变量之间互不影响；引用类型多个变量可以指向同一块对象内存，所以要靠 ARC 管理生命周期。比如 struct 改一个副本不影响原值，class 改属性可能大家都看到变化。坑是别把值类型一定在栈上、引用类型一定在堆上说死。

### 10. copy-on-write 是什么？

结论：它是值类型为了兼顾语义和性能做的延迟拷贝，真正修改前先判断底层存储有没有被共享。比如两个数组先共用一份存储，只有其中一个要改时才复制。这样既像值语义那样安全，又不会每次赋值都真拷贝。

### 11. 为什么 weak 只能修饰 class 类型？

结论：因为 weak 依赖运行时维护对象引用表，本质上跟踪的是堆上的对象实例，而 struct、enum 这类值类型没有这种对象身份。你可以把 weak 理解成“对某个对象地址做非拥有观察”，值类型拷来拷去没有稳定身份。面试里别把可选和 weak 混为一谈。

### 12. 页面不释放时一般怎么排查？

结论：我会先看 deinit 走没走，再用 Memory Graph 找强引用链，重点查闭包、Timer、通知、KVO、delegate 和单例缓存。比如页面退出后对象还挂在某个 block 里，一般一下就能看到。坑是只盯控制器本身，不去查它持有的子对象和任务。

## 二、多线程与并发

### 13. GCD 的串行队列和并发队列有什么区别？

结论：串行队列同一时刻只执行一个任务，并发队列可以同时推进多个任务。比如写文件、改共享状态我更倾向串行；图片下载、数据预处理更适合并发。注意队列是否并发，和你用 sync 还是 async 不是一回事。

### 14. 同步和异步分别是什么意思？

结论：同步说的是调用方要不要等结果，异步说的是先提交任务，当前线程可以继续往下走。比如 sync 像打电话必须等对方说完，async 更像发消息先去干别的。坑是很多人把异步等同于开新线程，其实不一定。

### 15. 同步/异步 + 串行/并发 四种组合分别有什么效果？

结论：核心是看“当前线程等不等”和“队列能不能并行”两件事。sync+串行最像排队办事，async+串行是不堵当前线程但任务还是一个个来；sync+并发一般少用，async+并发最常见。坑是主线程 sync 到主队列一定会死锁。

### 16. 在主线程里调用 DispatchQueue.main.sync 会发生什么？为什么？

结论：会死锁，因为主线程正在执行当前任务，却又同步提交一个必须等主线程空下来才能执行的任务。就像你自己把门锁上，再要求自己先出去开门。这个题面试里基本就是送分题，答清“互相等待”就行。

### 17. 为什么 UI 更新必须放到主线程？

结论：因为 UIKit 大部分对象不是线程安全的，主线程是它默认的事件、布局、绘制协调线程。你在后台线程改 UI，轻则表现错乱，重则直接崩。比如列表正在布局时另一个线程同时改视图层级，就很容易出奇怪问题。

### 18. DispatchGroup 的典型使用场景是什么？

结论：它适合等一组异步任务都完成后再统一收口。比如首页要并发拉 banner、推荐、活动，等三块都回来后再结束 loading。坑是 enter 和 leave 一定要成对，不然不是提前 notify，就是永远不回调。

### 19. DispatchSemaphore 能解决什么问题？

结论：它本质上是一个计数器，可以做限流、等待、资源竞争控制。比如我想最多同时下载 3 张大图，就可以用信号量控并发。注意它能解决部分同步问题，但别在主线程上乱 wait，不然非常容易把界面卡死。

### 20. 如何用信号量控制最大并发数？

结论：先设一个初值，比如 3，每个任务开始前 wait，结束后 signal，这样同一时刻最多就只有 3 个任务在跑。像停车场只有 3 个车位，没位子的新车只能先等。坑是异常分支忘了 signal，会把后面的任务全堵住。

### 21. OperationQueue 和 GCD 的区别？

结论：GCD 更轻量，适合直接调度任务；OperationQueue 更面向对象，支持依赖、取消、状态观察这些更工程化的能力。比如多个任务有前后依赖时，我更愿意用 Operation。面试里顺手提一句：底层调度最终还是会落到 GCD。

### 22. Swift 的 async/await 和 GCD 的区别？

结论：async/await 最大优势是把异步流程写得像同步代码，逻辑更线性，错误处理和取消也更自然；GCD 更偏底层调度。比如串联登录、拉配置、刷新页面，用 async/await 可读性会好很多。坑是写成 async 了不代表线程安全，数据竞争还是要自己管。

### 23. Actor 是什么？它怎么保证线程安全？

结论：Actor 可以把可变状态隔离起来，同一时刻只允许一个执行上下文去访问它的内部状态，从语言层面减少数据竞争。你可以把它理解成自带串行保护的对象。注意 Actor 解决的是状态隔离，不是所有耗时任务都该无脑往里塞。

### 24. 如何设计一个线程安全的单例？

结论：Swift 里最简单稳妥的写法就是 static let，语言层已经保证初始化只执行一次并且线程安全。真正要注意的反而不是“单例怎么生”，而是“单例里有没有共享可变状态”。比如缓存、登录态、配置中心都常做单例，但内部读写还得继续控并发。

## 三、列表性能优化

### 25. UITableView / UICollectionView 的 cell 复用机制是什么？

结论：复用的核心是屏幕外的 cell 不销毁，而是回收到池子里，后面新出现的位置再拿来重配数据。就像酒店退房后不拆房间，打扫一下给下一位住。坑是如果状态重置不全，就会出现错图、错文案、选中态串位。

### 26. reuseIdentifier 的作用是什么？

结论：它本质上是复用池的分类标签，让系统知道什么类型的 cell 可以互相复用。比如普通商品卡片和广告卡片样式不一样，就不能混着取。坑是不同布局硬共用一个 identifier，会把约束和状态问题放大得很明显。

### 27. prepareForReuse 一般做什么？

结论：它主要做状态重置，而不是重新塞业务数据。比如清空旧图片、取消未完成请求、恢复默认隐藏态和选中态。坑是把网络请求和复杂计算全塞进 prepareForReuse，会让复用阶段本身变重，反而影响滑动。

### 28. 图片列表为什么容易卡顿？

结论：因为图片链路很重，下载、解码、缩放、渲染任何一个环节放错线程都可能掉帧。尤其大图在主线程解码时，卡顿会特别明显。你可以把它理解成列表滚动时一边搬箱子一边开门，主线程很容易忙不过来。

### 29. 图片闪烁通常有哪些原因？

结论：最常见是 cell 复用后旧图没清、异步回调回到了已经复用的新 cell、占位图和真实图切换太频繁。比如第 1 行的图片请求慢，结果滑到第 10 行才回来，就可能把第 10 行的图覆盖掉。这个题最好结合复用和异步回调一起答。

### 30. 你怎么解决图片闪烁问题？

结论：我一般从三层做，第一是复用时重置状态，第二是给请求和模型做绑定校验，第三是命中缓存时尽量减少多余占位图切换。之前做 Feed 时就是先解决回调错位，再把刷新策略和图片赋值时机收紧，闪烁会明显下降。坑是只清图片不管请求回调，问题 usually 还在。

### 31. 图片从下载到显示完整经历哪些步骤？

结论：大致是发请求、拿到二进制数据、解码成位图、必要时缩放和解压、写缓存，最后主线程赋给 imageView 显示。真正吃性能的通常不是“设置图片”这一步，而是前面的解码和解压。面试里顺手提内存缓存和磁盘缓存，会更完整。

### 32. 为什么图片解码会导致掉帧？

结论：因为压缩格式像 jpeg、png 在真正显示前要先解成位图，这一步很吃 CPU 和内存带宽。如果把它放在主线程，列表正在滚的时候就很容易卡。就像你边开车边现场拆包装，显然会拖慢主线流程。

### 33. 图片解码应该放在哪个线程？

结论：一般应该放在后台线程做，处理好后再回主线程赋值 UI。很多成熟图片库本质上也都在帮你做这件事。坑是后台线程做好后还是要注意对象绑定，别把旧任务的结果塞到已经复用的新 cell 上。

### 34. 列表滑动卡顿怎么定位？

结论：我会先复现，再用 Instruments 看主线程热点，重点区分是布局、绘制、图片处理还是业务逻辑过重。比如 Time Profiler 看 CPU，Core Animation 看 FPS，必要时再看是否有离屏渲染。坑是没量化就开始改代码，很容易在错误方向上优化。

### 35. CPU 卡顿和 GPU 卡顿怎么区分？

结论：CPU 卡顿更像主线程干活太多，比如布局计算、JSON 解析、图片解码；GPU 卡顿更像渲染压力太大，比如圆角、阴影、混合过度。简单说，一个是算不动，一个是画不动。排查时结合 Time Profiler 和 Core Animation 看会比较稳。

### 36. 为了做到 60fps，你会从哪些方面优化？

结论：我会优先减主线程负担，像数据预处理、图片解码下沉后台，减少频繁刷新和复杂约束，其次控制渲染成本，比如规避不必要的离屏渲染。之前做 Feed 就是这么拆问题的。注意 60fps 不是只看一个点，要把数据、布局、绘制整条链路都压住。

## 四、网络与状态管理

### 37. URLSession 的基本组成有哪些？

结论：核心就是 session、task、configuration，还有 delegate 这套回调机制。你可以把 session 理解成工厂，task 是具体任务，configuration 是工厂规则。面试里能顺带说 dataTask、uploadTask、downloadTask 的区别，会更完整。

### 38. default、ephemeral、background 三种 configuration 的区别？

结论：default 是常规网络会话，会用缓存、cookie 等；ephemeral 更轻，不落持久化数据；background 适合后台传输，App 退到后台系统还能继续帮你跑。比如登录校验可用 ephemeral，上传大文件更适合 background。坑是别把 background 当成所有请求都更高级。

### 39. URLSession 的 delegate 和 completionHandler 两种方式有什么区别？

结论：简单请求用 completionHandler 更直接，流式处理、认证挑战、下载进度这类更复杂场景 delegate 更灵活。就像一次性办事和全程跟单的区别。坑是两套方式混用时要理清职责，不然状态和回调会很乱。

### 40. 乐观更新是什么？适合什么场景？

结论：就是客户端先把 UI 改了，让用户立刻看到反馈，再异步请求服务端确认，适合点赞、收藏、关注这类低风险高频交互。比如点收藏先亮星标，再把请求发出去。坑是涉及扣款、下单这类强一致场景就不能这么玩。

### 41. 乐观更新失败后如何回滚？

结论：失败后要把本地状态恢复，并且给用户一个明确但不打断流程的提示。比如点赞失败就把红心点回去，再弹个轻提示。注意回滚不只是改 UI，还要保证本地缓存、列表页和详情页这些多处状态一致。

### 42. 如何避免重复点赞 / 重复收藏？

结论：常见做法是本地先做状态锁或幂等控制，请求未完成前屏蔽重复点击，或者把多次点击合并成最后一次意图。比如快速点三下，我不会真发三次请求。坑是只在 UI 上禁用按钮，但底层请求层没有去重。

### 43. 如何防止旧请求覆盖新请求？

结论：核心是给请求绑定版本、时间戳或页面上下文，只接受最新一次结果。比如用户连续切筛选条件，先发的旧请求晚回来，也不能把新列表覆盖掉。这个问题本质上不是网络问题，而是状态时序管理问题。

### 44. 接口并发返回顺序错乱怎么处理？

结论：不要默认返回顺序等于发起顺序，应该在客户端做结果归属校验。比如搜索框连续输入 a、ab、abc，就只认最后一次 abc 的结果。坑是把 UI 更新直接写进回调里，不加任何上下文判断。

### 45. 请求去重一般怎么做？

结论：如果同一个页面、同一参数、同一时刻发了重复请求，我会在网络层或仓库层做合并，只保留一个实际请求，结果分发给多个调用方。像多人同时问前台一个问题，不用前台真跑三趟。注意去重要定义好 key，不然会误合并不同业务。

### 46. 弱网环境下你会怎么优化用户体验？

结论：核心是快反馈、可重试、能降级。比如先给骨架屏或本地缓存，按钮点击先有即时态，再根据结果修正；请求失败时给轻提示和重试入口。坑是弱网优化不只是调超时，更重要的是把用户感知链路设计顺。

### 47. 前后台切换时，正在执行的网络请求怎么处理？

结论：要按业务区分，像大文件上传下载可以交给 background session，普通页面请求一般在页面销毁或进入后台后考虑取消，避免无效回调。比如列表页退后台了，回来很可能已不是同一个上下文。坑是请求没取消，但页面对象已经释放，回调就容易出问题。

### 48. 如何设计一个统一网络层？

结论：我会把请求构建、参数编码、错误映射、日志埋点、重试和鉴权这些共性收口，业务层只关心接口语义。这样改超时、加 token 刷新、统一错误提示都比较省。坑是网络层别做得过重，别把所有业务逻辑都塞进去。

## 五、RunLoop

### 49. RunLoop 是什么？它解决了什么问题？

结论：RunLoop 本质上是线程的事件循环，让线程在有事做时处理事件，没事做时休眠，避免一直空转。主线程靠它处理触摸、Timer、网络回调这些事件。你可以把它理解成一个值班系统，有事唤醒，没事待命。

### 50. RunLoop 和线程是什么关系？

结论：一个线程可以有一个 RunLoop，但不是每个线程默认都跑起来，主线程的 RunLoop 是系统帮你启动好的，子线程通常要自己保活。坑是很多人以为开了线程就天然能接 Timer 和端口事件，其实没有 RunLoop 不行。

### 51. 主线程 RunLoop 是什么时候启动的？

结论：App 启动进入主消息循环时就已经由系统启动了，所以主线程天生能处理 UI 事件和 Timer。开发里一般感知不到它的启动动作，但会一直用到它。面试里别答成 viewDidLoad 之后才启动，那就错了。

### 52. RunLoop 常见 mode 有哪些？

结论：常见有 default、tracking 和 commonModes。默认模式下处理普通事件，滑动列表时系统会切到 tracking，所以一些默认模式下的 Timer 会停。坑是 commonModes 不是一个真正独立 mode，更像一组 mode 的集合标签。

### 53. UIScrollView 滑动时为什么 Timer 可能不执行？

结论：因为滚动时主线程 RunLoop 切到了 UITrackingRunLoopMode，而你的 Timer 默认加在 default mode 里，自然就收不到调度。解决一般是把 Timer 加到 commonModes。这个题本质考的是 RunLoop mode 切换，不是 Timer 自己失效。

### 54. 如何让一个子线程常驻？

结论：做法是在线程入口里主动启动 RunLoop，并给它加一个输入源或 Timer，防止线程跑完就退出。像早期一些网络库会这么做，专门让某个线程长期处理事件。坑是常驻线程不是越多越好，没必要就别自己造。

<a id="section-6"></a>

## 六、生命周期与页面管理

### 55. loadView、viewDidLoad、viewWillAppear、viewDidAppear 的区别？

结论：loadView 是创建根视图，viewDidLoad 是视图创建完适合做一次性初始化，viewWillAppear 是页面将出现，viewDidAppear 是已经展示到屏幕上。比如埋点、首帧相关逻辑就更适合放 didAppear。坑是把每次都要刷新的逻辑写进 didLoad。

### 56. 哪些初始化逻辑适合放 viewDidLoad，哪些适合放 viewWillAppear？

结论：一次性的 UI 构建、绑定、注册 cell 适合放 viewDidLoad；每次回来都可能变化的数据刷新、导航栏状态同步更适合放 viewWillAppear。就像房子装修一次，但回家前要先看看灯有没有开。注意频繁请求别无脑放 willAppear，容易重复打接口。

### 57. push 和 present 的区别？

结论：push 是走导航栈，适合层级式页面流转；present 更像模态展示，适合临时打断当前流程。比如商品列表进详情一般 push，登录弹窗、拍照页更常 present。坑是业务层级很深却滥用 present，后面返回关系会很乱。

### 58. UINavigationController 的 push/pop 生命周期调用顺序？

结论：push 时通常是当前页 willDisappear，新页 willAppear，然后当前页 didDisappear，新页 didAppear；pop 则相反。面试里不一定要逐字背顺序，但要知道两个页面的生命周期是交错发生的。坑是依赖某个回调做关键释放，却没考虑 push/pop 差异。

### 59. 页面返回时如何通知上一个页面刷新？

结论：常见做法有回调、delegate、通知、共享状态中心，简单场景我更倾向回调或状态同步，清晰且收敛。比如编辑地址页返回后，列表页根据回传结果局部刷新。坑是动不动就上通知，后面依赖关系会越来越难追。

### 60. 页面 pop 后为什么可能没有释放？

结论：本质还是被别的对象继续强持有了，最常见就是闭包、Timer、通知、KVO、delegate 写错、异步任务没解绑。比如网络层 completion 强抓 self，页面退了对象还活着。排查时一定先看 deinit，再顺着引用链找。

### 61. deinit 不走通常说明什么？

结论：说明这个对象生命周期还没结束，大概率存在强引用环或外部仍在持有它。对控制器来说，pop 后不走 deinit 基本就该警觉了。坑是有时不是控制器自己有问题，而是它持有的子 viewModel、manager 把它反向锁住了。

### 62. 通知、Timer、闭包、KVO 分别怎么导致页面无法释放？

结论：共同点就是页面退出后，这些机制背后还有东西在继续持有或回调这个对象。比如闭包强引用 self，Timer 强持有 target，KVO 和通知没解绑都会让对象生命周期拖长。经验上我会把这几项当成内存泄漏排查的固定 checklist。

<a id="section-7"></a>

## 七、国际化专项

### 63. iOS 多语言的基本实现方案是什么？

结论：标准方案就是按语言建多个 .lproj 目录，把文案放进 Localizable.strings 或业务 strings 文件里，再通过 NSLocalizedString 取值。这样系统会按当前语言自动匹配。坑是别把文案硬编码在代码里，不然后期维护非常痛苦。

### 64. Localizable.strings 怎么使用？

结论：就是定义 key-value，然后代码里通过 key 去取对应语言的文案。比如 title_order = "Order"，中文包里再给同一个 key 配中文。关键不是会不会调 API，而是 key 命名要稳定、可维护。坑是直接拿中文当 key，后期改文案会很麻烦。

### 65. stringsdict 是干什么的？

结论：它是专门处理复数和更复杂语法变化的，不同语言对 0、1、2 以上的规则不一样，不能简单靠字符串拼接。比如英文 1 item、2 items，阿拉伯语规则更复杂。做国际化外卖时，像商品数、分钟数这类场景非常常见。

### 66. 应用内切换语言怎么做？

结论：核心是自己管理一套当前语言配置，然后切换资源 Bundle，必要时重建根控制器刷新页面。也就是说不完全依赖系统语言，而是 App 内自己决定显示哪套文案。坑是切语言后别只刷新当前页，很多缓存页面和 tab 根结构都要考虑。

### 67. 为什么切语言后有的页面不会立刻生效？

结论：因为很多页面的文案是在初始化时就取好了，切语言只是改了资源来源，但现有界面不会自动重走一遍绑定。就像换了字幕文件，已经渲染好的画面不会自己更新。解决通常是页面重建或统一发送语言变更通知后重新绑定。

### 68. 语言切换后一般如何刷新界面？

结论：最稳的做法是重建 window 的根控制器，让整个页面树重新走一遍初始化；局部页面也可以监听语言变更后手动刷新。外卖这种多 tab 应用我更倾向全局重建，省得遗漏。坑是导航栈中间态和用户当前操作上下文要处理好。

### 69. 为什么日期格式、货币格式、数字格式不能写死？

结论：因为不同地区习惯完全不一样，日期有月日在前后的区别，货币有符号、小数位、千分位差异，数字也会受 locale 影响。比如 1,234.56 和 1.234,56 在不同国家含义不同。国际化里最忌讳把格式当成固定字符串。

### 70. Locale.current 和 en_US_POSIX 的区别？

结论：Locale.current 代表当前用户地区习惯，适合展示给用户看；en_US_POSIX 更适合做稳定、可预测的固定格式解析，比如和服务端约定时间串。简单说，一个偏本地展示，一个偏机器协议。坑是展示文案还用 POSIX，用户体验会很奇怪。

### 71. 12 小时制 / 24 小时制适配有哪些坑？

结论：核心坑是别自己硬写 HH:mm 或 h:mm a，而要结合 locale 和用户设置来格式化，不然海外版很容易显示不符合用户习惯。比如同样是下午三点，有人习惯 15:00，有人习惯 3:00 PM。项目里做时间展示时，这个点非常容易漏。

### 72. RTL 布局怎么适配？leading/trailing 和 left/right 的区别？

结论：做 RTL 最重要的是优先用 leading、trailing，它会跟阅读方向自动翻转；left、right 是绝对方向，不会智能适配。比如阿拉伯语下返回箭头、信息流图标朝向、文本对齐都要跟着翻。坑是很多自定义 view 里写死 left/right，国际化一上就露馅。

<a id="section-8"></a>

## 八、UIKit 核心机制

### 73. UIView 和 CALayer 的关系？

结论：UIView 更偏交互和事件管理，CALayer 更偏真正的内容显示和动画渲染，UIView 底层是通过持有一个 layer 来完成显示的。可以把 UIView 理解成前台经理，CALayer 是真正干活的舞台。坑是很多显示效果改 layer 就够了，不一定要重写 view。

### 74. 为什么 UIKit 要把 UIView 和 CALayer 分开设计？

结论：这样职责更清楚，视图负责响应和层级管理，图层负责高性能渲染和动画，解耦后扩展性更好。比如很多动画直接改 layer 属性就能做，不需要每次都走复杂视图逻辑。坑是别把 layer 当 view 用，它本身不处理触摸事件。

### 75. frame 和 bounds 的区别？

结论：frame 是这个 view 在父视图坐标系里的位置和大小，bounds 是它自己内部坐标系里的区域。比如一个 view 自己不动，只改 bounds.origin，也可能影响内部内容显示。面试里别只背“一个相对外部一个相对内部”，最好能举滚动视图的例子。

### 76. layoutSubviews 的调用时机？

结论：当 view 首次布局、尺寸变化、调用 setNeedsLayout 后，系统会在合适时机触发布局，最终走到 layoutSubviews。它适合放依赖尺寸的子视图布局，不适合写重业务逻辑。坑是里面再频繁触发布局，很容易造成性能问题甚至布局循环。

### 77. draw(_:) 的作用和调用时机？

结论：它是自定义绘制入口，只有系统认为需要重绘时才会调用，比如 setNeedsDisplay 后下一轮刷新。适合画图表、特殊形状，不适合拿来随便更新普通 UI。坑是 draw 里做耗时计算，会直接影响渲染性能。

### 78. 事件响应链是什么？

结论：就是触摸事件找第一响应者并沿着 responder 链往上传递的机制，没处理就继续往上交。比如点到一个按钮，先看按钮处理不处理，不处理再到父 view、controller、window。理解它以后，很多手势冲突和点击穿透问题会好排查很多。

### 79. hitTest(_:with:) 和 point(inside:with:) 的流程？

结论：pointInside 先判断点是否在自己可响应区域内，hitTest 再从顶层往下找最终该由谁接收事件。可以理解成先看“是不是我家范围”，再看“具体该谁开门”。坑是自定义扩大点击区域时，通常改 pointInside 更合适。

### 80. 手势识别器和响应链是什么关系？

结论：手势识别器是构建在事件分发之上的一层识别机制，它会先观察触摸序列，再决定是否识别成功，和原始响应链会互相影响。比如 tableView 里的点击手势和 cell 选中经常会有冲突。坑是多个手势同时存在时，要明确 delegate 和失败依赖关系。

## 九、架构设计

### 81. MVC、MVP、MVVM 的区别？

结论：它们本质上都在解决职责拆分，只是拆法不同。MVC 上手快但 controller 容易变胖，MVP 更强调 presenter 调度，MVVM 更适合把页面状态和视图绑定分开。实际项目里我更关注是不是把网络、状态、路由这些从 controller 里拆出去了。

### 82. 为什么 iOS 项目容易出现 ViewController 过胖？

结论：因为 VC 天然拿得到视图、生命周期、导航和事件入口，很容易顺手把网络、埋点、状态管理全写进去。时间一久它就像一个什么都管的总包。坑是过胖不是代码行数问题，而是职责耦合导致难测、难改、难复用。

### 83. 什么叫配置化？为什么配置化能降低迭代成本？

结论：配置化就是把一部分页面展示规则、筛选项、样式或行为从硬编码抽出来，改数据或配置就能驱动变化。比如资源筛选项如果做成配置，下次加一个条件不一定要发版改死代码。坑是配置化也有边界，别把复杂业务流程全配成脚本。

### 84. 页面路由一般怎么设计？

结论：我会把页面跳转抽成统一路由层，外部只描述“去哪里、带什么参数”，不要到处直接 new controller 再 push。这样页面解耦、埋点和降级也更好统一。坑是路由层别变成万能大杂烩，参数校验和兜底要做清楚。

### 85. 状态流混乱一般体现在哪些问题上？

结论：典型表现就是同一份状态有多处来源，列表页、详情页、缓存层各改各的，最后 UI 不一致。比如收藏状态在一个地方改了，另一个页面没同步，就会出现来回跳。这个问题本质不是刷不刷新，而是谁是单一可信源。

### 86. 如何设计一个统一的业务状态管理方案？

结论：核心是收敛状态来源，明确谁负责持有、谁负责修改、谁只负责展示。比如商品收藏态可以统一落在仓库层或 viewModel 层，再把变更分发给页面。坑是状态管理别为了“高级”搞得过重，能解决同步问题就够了。

## 十、Swift 基础

### 87. struct 和 class 的区别？

结论：最核心的区别是值语义和引用语义，struct 赋值传参会复制语义，class 是共享同一个对象；另外 class 支持继承和 deinit，struct 不支持。比如轻量数据模型我更倾向 struct。坑是别机械地说 struct 一定更快，要看场景。

### 88. Optional 的本质是什么？

结论：它本质上是一个枚举，要么有值 some，要么没值 none，不是语法糖这么简单。Swift 用它把“可能为空”这件事放到类型系统里强约束。这样你在编译期就得处理空值，不像很多语言把风险拖到运行时。

### 89. 强解包为什么会 crash？

结论：因为你在告诉编译器“这里一定有值”，如果运行时其实是 nil，程序就只能直接崩。就像你闭眼踩台阶，结果前面其实是空的。面试里最好顺手补一句：能用可选绑定就别强解包，尤其是网络数据和 IBOutlet 这类不稳定来源。

### 90. guard let 和 if let 的区别？

结论：两者都能解包可选，区别是 guard 更适合前置校验，失败就尽早返回，解包后的变量作用域还能继续往后用；if let 更适合局部条件分支。写业务代码时 guard let 往往更清晰。坑是 guard 不是更高级，只是更适合做早退出。

### 91. protocol + extension 怎么实现默认实现？

结论：先定义协议，再在 extension 里给出默认方法实现，这样遵循协议的类型可以直接复用，也可以按需重写。很适合抽公共能力，比如埋点、日志、页面标识。坑是协议扩展里的静态派发细节要有概念，不然多态预期可能和你想的不一样。

### 92. Codable 的基本用法是什么？

结论：让模型遵守 Codable 后，通常就能直接和 JSON 做编解码，简单场景非常省代码。比如接口返回商品列表，只要字段对应得上，JSONDecoder 一把就能转。坑是字段名不一致、时间格式特殊、嵌套结构复杂时，要配 CodingKeys 或自定义解码。

## 十一、崩溃排查与监控

### 93. iOS 常见 crash 类型有哪些？

结论：常见有数组越界、强解包 nil、消息发送异常、KVC/KVO 异常、线程问题和内存访问问题。对 Swift 项目来说，强解包和越界会更常见一些。面试里别只报名词，最好顺手说一两个真实业务场景，比如接口字段为空导致解包崩。

### 94. 线上 crash 一般怎么定位？

结论：我会先看崩溃堆栈和发生版本，再结合符号化、用户操作路径、设备系统版本去还原现场。很多时候先确认是必现还是偶现，再决定是代码逻辑问题还是环境兼容问题。坑是只看第一帧就下结论，很多异步问题真正根因不在最表层。

### 95. dSYM 是什么？为什么重要？

结论：它是符号文件，能把线上拿到的内存地址还原成可读的方法名和代码位置，没有它崩溃日志基本就像天书。就像地图坐标没图层，只剩一串数字。注意发版后 dSYM 一定要和对应构建版本保存好，不然补都不好补。

### 96. Instruments 常用哪些工具，分别看什么？

结论：排性能我最常用 Time Profiler 看 CPU 热点，Core Animation 看渲染和 FPS，Allocations/Leaks 看内存问题，Memory Graph 看引用关系。比如列表卡顿先看 Time Profiler，页面不释放先看 Memory Graph。坑是工具很多，但一定要先带着问题去看，不然容易迷路。

## 十二、结合简历的项目深挖

> 这一组建议你背框架，再替换成自己的真实排查过程、数据口径和取舍。

### 97. 你说优化了 Feed 刷新策略，具体改了什么？

结论：我会优先从减少无效刷新和稳定 cell 状态入手，比如把全量 reload 收敛成局部刷新，避免滚动中频繁改整段列表，同时把数据源更新和 UI 刷新时机对齐。这样做的好处是主线程压力更可控，列表不会因为状态震荡出现跳动。坑是局部刷新前要保证索引和数据绝对一致。

### 98. 图片闪烁的根因是什么？你最终是怎么解决的？

结论：根因主要是 cell 复用和异步图片回调错位，旧请求结果回来了却落到了新模型上，再加上占位图切换频繁就更明显。我最后会做请求和模型绑定校验，复用时清理旧状态，缓存命中时减少重复 setImage。这样一般能把错图和闪烁一起压下去。

### 99. 你说弱网反馈延迟压缩到 100ms 内，具体是怎么做到的？

结论：核心不是让网络真的 100ms 返回，而是让用户 100ms 内感知到系统已经响应。我会用乐观更新先改本地态，比如点赞收藏先反馈，再异步请求，失败再回滚并提示；同时减少主线程多余工作，保证点击后 UI 立即可见。坑是这种方案只适合低风险、可回滚的操作。

### 100. 搜索筛选配置化、状态流收敛、页面路由一致性，你具体做了什么？

结论：我的思路是把筛选项和部分展示规则从页面代码里抽出来，让配置驱动 UI；状态上明确单一来源，避免列表和详情各改各的；路由上统一入口和参数校验，减少页面跳转分散实现。这样后续加筛选、改跳转和处理异常回滚都更稳。坑是配置化边界要控制住，不然会变成另一套难维护系统。
